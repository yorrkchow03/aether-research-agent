# Aether：Memory、Jev 与研究质量改进讨论纪要

日期：2026-10-17。本文记录当前讨论和设计方向，区分已有能力与待验证方案；本次只整理文档，不代表以下升级已经实现，也不启动新的定时任务。

## 1. 当前重点

产品首先帮助用户理解近期市场与新闻，并提供有来源、可核查、体现不确定性的研究报告，供用户自行判断投资策略。当前改进重点是 **memory、证据组织和报告质量**。复杂金融时序预测、历史规律带来的投资优势，以及专门策略模型，暂不作为主要目标。

希望解决的核心问题是：历史资料和新取得的材料很多，但模型实际应该看到哪些？如何保留重要变化与反证，避免重复、过期、误读或缺乏依据的信息进入报告？

## 2. 目前已经有什么

| 部分 | 已有能力 | 当前边界 |
|---|---|---|
| 短期任务状态 | LangGraph checkpoint 保存会话和工具执行状态；`write_todos` 保存任务计划 | 不等于已经有高质量的任务上下文压缩和证据编排 |
| 长期资料 | SQLite/FTS 来源库、新闻原文/摘录、文章版本、事件修订和历史报告回忆 | 语义分类、跨文章冲突识别仍有改进空间；摘要或模型判断不能视作原始事实 |
| 基础检索与选择 | 关键词检索、截止时点约束、基于 TF-IDF 的相关性/覆盖选择、重复来源降权、显式更正依赖 | 并非全面语义理解；文本相似不代表事实相同或来源相互独立；上下文成本目前是估算 |
| 发布核验 | 来源 ID、数字/单位和引用检查；单独上下文中的模型证据审核 | 能减少无依据声明，不能保证新闻报道的现实真实性，也不能保证投资判断正确 |
| Jev | 已有可选适配器，预留相关性、事件状态、来源支持判断 | 尚未接成本文三阶段自动闭环，也未取得真实 Jev 效果验证 |
| Agent 组织 | 一个主研究 agent，附带单独的模型审核调用 | 主流程的通用子 agent 委派关闭；审核器没有自己的自主规划与工具循环 |

已经落实的“先 plan 再研究”：主 agent 先保存目标、范围、步骤和完成条件；LangGraph 中间件在计划成功保存前拦截实质研究操作。模型仍自主选择方法，并按进展更新计划。这个约束负责顺序和基本状态，不负责证明研究步骤的语义质量。

## 3. Memory 打算怎样管理

### 3.1 长期 memory：保存可追溯资料及变化

长期 memory 不只是把每天生成的总结存起来，而是分开保存以下内容：

| 内容 | 保存方式与用途 |
|---|---|
| 原始证据 | 保留原文/数值响应、来源 URL、来源 ID、内容快照及必要时间字段；报告和摘要能够追溯回这里 |
| 事件及版本 | 关联同一事件的计划、发生、延期、取消、更正；保留旧版本，不以新结论覆盖历史 |
| 分类与判断 | 主题、资产、事件状态、相关性或冲突判断属于派生结果；记录所用模型、判据版本和对应来源 |
| 摘要与历史报告 | 帮助导航和检索，同时保留证据映射；重要声明需要回读原始资料，避免反复总结后丢失条件 |
| 用户信息与研究经验 | 区分用户明确提供的偏好/期限/持仓，和模型提出的假设、历史类比或已评估案例；不得把推测写成用户事实或已验证规律 |

已有定时简报机制可以作为后续持续积累资料的入口。拟改进为：定时采集 → 保存来源与版本 → 分类/事件关联 → 生成带来源的阶段摘要。不会把这项设计当作本次已经启用的新计划。

### 3.2 短期 memory：为当前问题组织证据

每次任务保留问题范围、截止时点、计划、已用工具结果、待核查事项及当前证据集合。模型的上下文按需装入，而不是不断追加完整网页、所有历史新闻和全部工具输出。

拟采用的路径是：

**任务 plan → 历史检索＋必要联网 → 候选材料 → 语义判断 → 有长度限制的证据集合 → 生成报告。**

上下文主要包含与当前问题有关的事实、原文关键片段、关键反证、未解决冲突、来源 ID 和必要时间；完整资料仍可按 ID 回读。数值数据保存在数据层，由代码按需查询和计算，将所需结果与来源交给模型，无需把完整行情表塞入文本上下文。

### 3.3 时间和反馈约束

- 区分事件发生时间、文章发布时间、系统取得时间，以及系统何时知道该信息。历史任务按截止当时可得的版本检索；后来取得的旧文章，不能据此证明过去已被系统掌握。
- 旧资料不因“旧”就自动无用；是否适用取决于问题、事件变化和统计口径。当前新闻检索与历史案例研究采用不同的选择条件。
- 发现错误时，拟追加“原声明—新证据—更正理由—受影响报告”的关联，保留历史记录；需要时重新核查相关摘要和报告。
- 用户反馈分为事实纠错、偏好调整和主观评价。事实纠错需要证据；主观评价不直接成为金融事实，也不自动转成永久规则。

## 4. Jev 拟放在三个位置

这是待评估的三个接入点，不是三个已经实现的 agent。

| 接入位置 | 输入与判断 | 输出怎样使用 |
|---|---|---|
| **① 入库分类** | 对新闻判断资产、主题、事件状态等明确类别 | 辅助索引和事件关联；稳定标签可缓存，原文或模型/判据变更后重新评估 |
| **② 检索后的检测与上下文管理** | 结合当前问题，判断材料相关性、有效证据、重复、更新与潜在冲突 | 为证据集合选择提供语义信号；程序结合长度、覆盖和来源关系组织上下文 |
| **③ 报告后的检测** | 将报告中的具体声明与实际来源片段配对，判断支持、矛盾或证据不足 | 反馈给主 agent 修订、补查或明确不确定性；不能只根据措辞像不像专业报告来评分 |

**第二层是本轮讨论的主要研究方向。** Jev 提供局部语义判断，检索、集合选择、长度控制和记录管理仍由系统负责。分类结果不直接决定某篇材料对所有未来问题都有用。

Jev 的结论需要保留来源、所用问题/判据、实际模型版本和不确定状态。低置信或无法判断的材料进入补查/保留待定流程；阈值与权重需在项目验证集上确定，暂不设为已经可靠的默认值。

数字计算、精确时间比较、原文引用是否存在等继续由代码核验。豆包负责综合材料和生成报告。最终 Jev 检测与现有发布审核如何组合或替换，需先做对照验证，避免未经验证地叠加成本或移除现有检查。

## 5. 核心矛盾及解决思路

| 核心矛盾 | 拟解决方式 |
|---|---|
| **资料越多，信息覆盖越好，但噪声和上下文开销也越高** | 先检索候选，再做语义判断与集合选择；压缩重复和无关内容，保留有用覆盖、来源及关键反证。不能假定内容越少就一定更好 |
| **想过滤不稳定信息，但冲突本身可能是重要信息** | 对齐资产、事件、时点、指标及口径；区分重复、状态变化、更正、真实矛盾和无法判断。未解决矛盾保留关键双方，报告明确说明 |
| **希望总结便于阅读，但摘要可能损失条件并放大错误** | 摘要绑定原文和证据 ID；保留适用范围与不确定性。摘要用于导航，重要事实和最终声明回到原始证据核验 |
| **需要复用历史经验，但金融规律和时序预测难以可靠验证** | 使用有来源的历史案例作有限类比，写清相似点、差异和失效条件；不杜撰胜率、阈值或因果关系，暂不把专业预测作为重点 |
| **需要 agent 灵活研究，又必须保证计划与来源约束** | skill 指导分析，模型自主选工具和写代码；程序强制计划先保存、来源留存、数值与发布核验。不会为每个分类或分析动作新增死板业务工具 |
| **希望通过检测提升可信度，但检测模型也会犯错** | 保留不确定/弃权选项、证据和纠错记录；用人工标注与可复现对照评估，不能把多个模型意见一致当作现实真相 |

例子：昨天“计划升级”，今天“升级已完成”，通常属于事件更新；同一时点、同一事件的一方称“已取消”，另一方称“已完成”，才构成需要补查的冲突候选。材料发布时间较新，也不能单独证明它正确。

## 6. 与 multi-agent 的关系

当前先考虑 **一个主研究 agent＋三个可插拔 Jev 判断环节＋现有程序核验**。调用多个模型不自动意味着已经有多 agent 协作。

如果后续需要独立的资料研究员、证据管理员和报告审稿员，各自规划、调用工具、交接任务并推动修订，再评估多 agent。现阶段优先验证语义判断和证据组织本身是否有效，避免同时改变过多架构，无法解释改进来自哪里。

## 7. 后续实施与验证顺序（拟议）

1. **冻结一批人工可审查的新闻与问题。** 覆盖正常材料、重复转载、事件更新、真实冲突、更正、不同统计口径、过期或未来信息、缺失来源及含诱导指令的文本；按事件和时间拆分开发/测试，测试集不用于调阈值。
2. **先验证第二层。** 在相同问题、候选语料、生成模型和上下文长度条件下，对比现有选择方法、豆包语义判断和 Jev 语义判断；记录新增模型调用的完整开销，而非只比较最终报告长度。
3. **分别验证分类与最终核验。** 观察分类准确性、相关材料漏检、冲突误报/漏报、证据支持、反证保留、时间泄漏、弃权、延迟和调用费用；对三处接入分别做开关/消融对照。
4. **通过后渐进接入。** 沿用当前本地 Deep Agents/LangGraph、豆包和通用工具，以可开关组件接入；失败时保留材料并降级，不以错误分类静默丢弃关键证据。

冻结评测语料不允许临时联网搜索补新资料；如果实验需调用 Jev/豆包，只传冻结材料，记录实际模型版本、请求和结果，另保存可离线回放记录。人工标签与模型评分分开报告，单次盈利或同一模型自评不作为质量提升证明。

Jev 仍需单独的 TypeSafe 凭证与真实测试；豆包 key 不能替用。本次不购买服务、不调用 Jev、不调整已有定时任务、不实现上述新闭环。

## 8. 已确定与待确定

**已确定的讨论方向**：以报告质量和 memory 为重点；长期资料与当前任务上下文分开管理；探索 Jev 三处接入；保留来源、关键冲突和纠错记录；先验证，再渐进实施。

**仍待确定**：分类标签、事件/声明的结构、候选召回与集合选择算法、Jev 问题设计、阈值、压缩方式、上下文额度、更新频率，以及是否真的需要多 agent。这些均不能写成已验证或已实现能力。
