# Aether 历史资料库建设评估

评估日期：2026-10-26。建议先沿用本地 SQLite 与原始文件存储，建设统一的数据目录、版本与采集记录，再用小规模试点决定历史新闻范围和是否需要更多技术组件。后续可扩展至数千到万篇资料，但本轮不执行批量下载、迁移、模型分类或定时采集。

## 1 项目需要怎样的资料库

资料库首先应当能够回答三个问题：某个时间段发生了什么；每个数字或事件来自哪里；当前研究与过去的资料、报告有何关联。Memory 和 Jev 使用这个资料库组织上下文；摘要、向量索引和模型分类都是可重建的派生结果。

建议首先集中 ETH，以 BTC 为市场参照。资产、交易所和报价币种分别标识；Coinbase 的 ETH-USD 与 OKX 的 ETH-USDT 永续数据不能合并成一种未注明口径的 ETH 行情。

| 类别 | 建议覆盖 | 主要用途 |
|---|---|---|
| 市场时序 | 复用已有多年日线，后续试补最近一年小时线 | 报告里的走势、成交量和指标计算 |
| 衍生品与生态 | 资金费率、OI、TVL 等逐项记录实际可得历史范围 | 市场背景；不要求所有指标起止时间相同 |
| 新闻与公告 | 官方公告、治理材料、有限的可信媒体；优先近 6–12 个月 | 近期研究、事件关联、Jev 与 memory 实验 |
| 外部研究报告 | 来源明确、可以取得与保存的报告或公开说明 | 较长期的背景材料；与新闻类型分开 |
| 本系统报告 | 成功发布的回答、报告、引用和审核记录 | 回忆过去研究，追踪结论变化；不作为独立外部事实来源 |
| 实验材料 | 带版本和 manifest 的冻结语料、标签、划分 | 可复现评测，与持续更新的产品资料分开 |

这里的“覆盖”是采集目标，不是现有完整性承诺。新闻不足时不以转载数量补足独立来源，更不将摘要计作全文。

## 2 当前基础与优先修补项

上一轮只读盘点显示，主知识库有 2,314 条证据，其中 2,147 条为数值及派生记录，104 条为搜索摘录，40 条为 feed，23 条为 page 证据。新闻正文索引对应 8 个 URL、13 个版本；page 证据条数与唯一文章/版本数不同。另有 9 份报告、7 份回答和 8 条事件版本记录。

已有 ETH/BTC 冻结日线各 2,480 根，覆盖 2020-01-01 至 2026-10-15；memory pilot 的 13 篇官方文章也存放在独立验证目录。这些实验材料未必全部处于日常主库的统一检索范围内，不能将某一张表的统计当作整个项目资产总量。

主库的新增证据停在 10 月 17 日。新闻版本有 16 条缺少发布时间，另有 2 条早于 2000 年的可疑日期。应保留原记录并追加质量标记与清洗版本；不删除历史收据，也不使用抓取时间冒充文章发布时间。

### 存储测量

本轮只读统计：knowledge.sqlite 文件为 139,804,672 字节，约 140 MB；其中 data 类证据 JSON 的 UTF-8 序列化内容合计 135,093,553 字节。相关数值原始文件另占约 117 MB，尚未统计项目全部缓存、副本与实验快照。

当前 page 类证据引用的 14 个不同原始文件合计约 3.54 MB，中位大小约 196 KB。这是很小且有偏的本地样本，只能用于容量规划的初始假设。

当前优先问题是重复快照、大 JSON 和分散的资料目录，不是数据库引擎达到容量上限。runtime 的 bootstrap 主要回收会话内的收据/报告/回答，不能直接视为覆盖全项目文件和冻结语料的完整迁移器。

## 3 历史资料从哪里取得

| 数据 | 推荐路径 | 已核对的可行性与限制 |
|---|---|---|
| Coinbase 日线/小时线 | 沿用已有 API 与分页思路，按时间窗口回补 | 官方每次最多 300 根；可返回窗口前的数据，必须裁剪、去重；官方也说明历史可能不完整，需核对缺口。[1] |
| OKX 资金费率 | 近期 API 加官方历史档案 | 官方档案页面列出自 2022 年 3 月起的资金费率；不表示每个合约都从该日存在，需检查实际文件。[3] |
| OI | 单独查清可用端点、频率与最早日期 | 不将当前 OI 快照冒充历史；本轮未确认能够免费补齐目标历史范围 |
| TVL/费用等 | 现有 DefiLlama 适配器，按指标试查历史 | 官方 Open 层提供基础数据；Pro 网页套餐与 API 套餐不同。先用可用基础接口，额外类别再评估。[4] |
| 官方新闻/公告 | 发布方历史列表、文章页、RSS、站点索引 | Ethereum Foundation 与 Bitcoin Core 可作为候选起点；RSS 的近期列表不等于完整历史档案。[5][6] |
| 媒体新闻 | 少量来源白名单、历史页面；搜索/GDELT 用于发现 URL | 发现链接不等于取得原文；付费墙、删除、动态页面和来源条款都可能降低全文覆盖 |
| 外部报告 | 发布方报告页或合法公开文件 | 保留发布机构、版本与报告类型，付费或无法取得的材料标为缺口 |

Coinbase 公共 API 官方列出的限额是每 IP 每秒 10 次、突发 15 次；采集器应远低于上限运行，并保存游标、对 429 退避，而不是让每个研究问题重复抓完整历史。[2]

OKX 的批量历史接口在官方更新日志中有记录，2026 年 8 月还调整过单次查询跨度。历史下载与近期接口需要分别评估，不能仅凭当前适配器 limit=100 推断只能取得 100 条历史。[3]

GDELT DOC 可以作为新闻发现候选，但官方早期说明对 ArticleList 时间窗口有限制。本轮没有实测当前历史查询范围与召回完整性，不能将它承诺为一键完整新闻档案。[7] 小试点应比较它与发布方历史列表是否发现相同的目标文章。

建议先使用公开来源；当试点明确发现重要资料缺口，再评估有许可的商业新闻接口。此处不购买或开通任何服务。

## 4 建库方式比较

| 方案 | 适用场景 | 收益与代价 | 本项目建议 |
|---|---|---|---|
| 原始文件 + SQLite/FTS | 本地运行、低写并发、数千至万篇资料与中小规模时序 | 复用现有代码、容易备份与快照；需控制大 JSON、索引与写事务 | 第一阶段采用 |
| 上述方案 + Parquet/DuckDB | 较多资产/频率的批量时序分析、反复实验 | 列式文件和按列/条件读取；增加文件发布、分区与版本协调 | 预留扩展，不在试点前强制加入 |
| PostgreSQL 等中心服务 | 多人跨机器共同写入、公开部署或明确的并发需求 | 中央权限与事务管理；需部署、备份、连接与迁移维护 | 需求出现再选 |

SQLite 官方强调本地存储和低写并发场景，单库同一时刻只有一个 writer；因此由统一采集写入队列负责短事务，而非让多个成员同时修改共享网盘里的数据库。[8]

DuckDB 能直接查询 Parquet，并支持列和过滤条件下推，适合将来反复扫描较大时序文件。[9] 当前一年的 ETH/BTC 小时线理论上仅 2 × 365 × 24 = 17,520 行，不需要为此立即引入新服务。这个行数假设每个小时都有有效数据，完整性仍要按来源检查。

向量检索可以后续增加，但向量库只是检索索引，不能替代原文、版本和结构化行情。先保留现有 FTS 基线，才能评估新检索是否实际改善召回。

## 5 推荐的数据结构

这些是同一数据层中的逻辑对象，不要求分别部署数据库。

| 对象 | 核心内容 |
|---|---|
| source_registry | 来源、数据类别、入口、频率、实际覆盖、访问/保存/共享条件、责任模块 |
| raw_objects 与 captures | 原始响应内容哈希、路径、字节数；每次实际请求的时间、状态与原始对象引用 |
| documents 与 versions | 文章身份、来源 URL、原文版本、正文抽取版本、发布时间及其证据 |
| market_observations | 资产、venue、instrument、报价币种、频率、区间、数值、单位和修订身份 |
| events 与 relations | 事件身份，关联文章、状态更新、明确更正及待核查的矛盾关系 |
| research_outputs 与 claims | 系统报告/回答、声明、引用、计划和审核结果；外部报告另有材料类型 |
| annotations | Jev/豆包等派生判断，输入版本、判据版本、实际模型、概率、耗时及用量 |
| ingestion_runs 与 coverage | 采集任务、游标、失败、重试、缺口和最新可得数据 |
| dataset_snapshots | 验证集用到的确切来源版本、划分、manifest 和许可/共享边界 |

### 去重与版本

原始内容按哈希复用，同样的内容再次取得时只追加 capture，不再复制整份正文。归一化行情按交易场所、交易对、频率、区间建立稳定键；重复读取的同一根 K 线只保存一次有效版本，并保留各次观察和修订来源。指标计算按输入版本与代码版本生成派生记录。

不同媒体转载同一消息，可以关联为同一事件或转载簇，但保留各自文档身份。相似不自动等于重复，更正或矛盾的双方也不能因去重被删除。

### 时间

至少区分：事件/行情发生时间、来源声称的发布时间、系统取得该版本的时间、库内入库时间。发布时间应有解析来源和可信状态。

今天回补一篇去年的文章，只能确立“今天取得这个版本”；不能直接证明去年看到的内容与今天相同。历史研究应区分“事后重建资料集”与“当时已取得的资料集”，并在截止查询中落实，不只写在报告说明里。

## 6 如何与当前 agent 衔接

采集器负责有界、可恢复的来源访问和入库；无需每次采集启动一个完整研究 agent。近期 feed 和已闭合 K 线可以定期增量取得；搜索、原文补抓和模型标注按需求进入独立队列。具体频率在试点后决定，不在本轮新增定时任务。

主 agent 继续使用现有工具与 ResearchClient。通过兼容层查询新的资料目录/索引，保持旧 record_id 可解析、原始哈希与报告引用不变，不要求为每个数据库表新增业务工具。

历史回补任务与近期更新使用同一个限速器与来源质量契约；按资产/日期/事件保存进度。失败保留 reason、HTTP 状态、下次重试信息，不把接口不可用或正文抽取失败记为“没有新闻”。

Jev 可在新文章/新版本上生成可缓存分类；检索后的相关性与冲突判断受当前问题影响，需要另一层缓存键。不要让所有文章两两比较：10,000 篇就有 49,995,000 对。先用资产、时间、事件及 FTS 形成小候选集，再进行语义判断。

## 7 规模与费用估计

以下是讨论用目标，尚未取得或承诺达到。

| 阶段 | 资料目标 | 目的 |
|---|---|---|
| 小试点 | 100–300 篇不同文章，少量有更新/更正的事件；两资产一个月小时线 | 测正文完整度、时间、重复、来源连接、恢复与使用体验 |
| 第一版资料库 | 近 6–12 个月、约 3,000–10,000 篇文章；多年日线与一年小时线 | 支持实际研究和冻结的 Jev/memory 对照；数量取决于来源质量与取得条件 |
| 后续扩展 | 更多来源、资产和更长窗口 | 用查询、写入、来源覆盖及维护指标判断是否需要扩技术栈 |

按当前少量原文样本约 200 KB/原始文件估算，10,000 个版本约 2 GB 原始内容；正文、索引、多版本和一份独立备份另外占空间。可先预留 5–10 GB，实际倍率须由试点测量；这不是压缩后容量或性能测试结果。

硬盘与基础软件可复用本机。公开接口的访问限制、正文获取质量和人工审核更可能是成本瓶颈。持久化资料不能跟随 TTL 缓存一起清除；备份须包含 SQLite 一致性快照、原始文件与 manifest，先验证能恢复，再安排长期运行。

Jev 官网输入价格为每十亿 token 42 美元。[10] 若每篇单次实际计费输入假定为 3,000 token，10,000 篇一次处理为 3,000 万 token，按此单价约 1.26 美元。这只是一个分类阶段的输入费用估算，不含再次判断、候选配对、重试和报告核验，也不是整条流程账单。豆包 Plan 的请求/额度消耗应单独记录，不能折算成不存在的免费调用。

## 8 小试点建议与验收

本轮只提交评估。若之后确定实施试点，可按下列顺序推进：

1. 只读目录盘点并生成 manifest，区分生产资料、测试合成内容、历史研究和冻结确认集；保留现有数据库的可恢复备份。
2. 在独立试点目录导入现有 ETH/BTC 时序与少量文章，保留旧证据 ID，不接管生产写入。
3. 对选定的官方/媒体来源少量补抓，覆盖近期与较早时间，抽查正文和日期；记录失败与访问条件。
4. 对相同输入运行两次采集，确认文档/行情不会重复膨胀；模拟中断后续接与一份更正版本。
5. 以真实研究问题检查“时间范围 + 资产 + 事件 + 原文 + 行情 + 报告引用”的联合查询，再测索引大小、延迟和写入锁等待。
6. 将一小份来源版本及标签冻结，验证后续新增材料不会改变既有测试集；备份恢复后逐项比较 hash 与查询结果。

应带回共同评估的指标：URL 到可用正文的成功率、无标题/缺段/导航污染情况、时间缺失和错误率、有效文章去重率、按天/来源/资产的覆盖缺口、取得一篇资料的实际请求与人工检查量、查询延迟、存储增长、引用解析成功率及恢复结果。有限白名单可检查其已列出的目标文章；全网相关新闻的绝对召回率不能由这个试点确定。

不以篇数达标代替这些检查。小试点的阈值应先共同确定，再评估是否扩展；新添的确认集在调试阶段保持未查看。

## 9 共同决定的事项

- 是否继续以 ETH 主研究、BTC 参照作为第一版范围。
- 历史新闻先覆盖近 6 个月还是 12 个月；更久以前先围绕选定事件补充。
- 是否优先公开原文来源，商业新闻仅在明确缺口后评估。
- 数据集中在本机运行，还是需要多人远程共同写入；后者会改变数据库部署选择。

推荐讨论基线：**本地原始文件 + SQLite/FTS；100–300 篇试点；通过后逐步扩到近 6–12 个月的数千篇资料。** 保留未来 Parquet 分析与中心数据库接口，先不迁移主库。
