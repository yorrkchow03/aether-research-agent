# Aether 项目总览与后续研究路线

核对日期：2026-10-26，Asia/Shanghai。本文依据当前源码、交付 manifest、已保存验收和本次离线框架自检整理。没有在本次盘点中刷新行情、运行付费模型或复测报告语义质量。

## 1. 项目定位

Aether 是面向个人的加密资产研究工作台，重点研究 ETH，以 BTC 为市场参考。系统获取数值数据与新闻，保留来源和时间，组织历史资料，生成可核查的研究报告与条件建议，供用户作出自己的投资判断。

后续研究重点是 **Jev 如何改善证据处理、memory 上下文选择和报告核验，并与豆包比较质量、时间及调用消耗**。现有产品提供真实应用环境和实验基础；金融时序预测、自动交易及更多页面不作为下一阶段的主要投入。

## 2. 实际架构

```text
网页 / 定时研究请求
          ↓
FastAPI → AgentRuntime → 本地 Deep Agents / LangGraph
                             ↓
                      保存本次研究计划
                             ↓
              豆包 Pro 自主选择工具、读 skill、写 Python
                             ↓
     数值 API / 联网搜索 / 原文抓取 / 历史 memory / 计算
                             ↓
        来源与数字检查 + 单独上下文中的豆包证据审核
                             ↓
                    发布回答、报告及来源

Jev：可选适配器已接通；三阶段自动闭环仍待开发和评估。
```

| 组件 | 当前实现 |
|---|---|
| Harness | Deep Agents 0.7.23、LangGraph 1.2.14、LangChain 1.4.4 |
| 主模型 | doubao-seed-2.1-pro，经授权的 Ark /api/plan/v3 |
| 指令 | prompts.py 定义角色与发布边界；planning.py 强制每个研究 job 先成功保存计划 |
| Skills | research、quantitative-analysis、strategy-research、portfolio-analysis，共四个 |
| 业务工具 | 12 个；负责来源访问、记忆、证据和提交等边界 |
| 通用工具 | execute、ls、read_file、write_file、edit_file、glob、grep、write_todos，共八个 |
| SDK | 活跃任务内通过 Unix socket 访问同一数据服务；16 个操作，不向终端传递模型 key |
| 终端 | 在真实本机执行模型编写的代码；不是容器隔离或多用户安全沙箱 |
| Agent 组织 | 主研究流程为单 agent；证据审核是独立上下文调用，不具备自主工具循环。通用子 agent 委派关闭 |

可选 Strategy Lab 的作者/评审实验有独立的有界多角色流程；不能因此把主研究流程描述为已完成多 agent 改造。

## 4. 获取信息与 memory 的准确理解

### 数值数据

数值数据保存在数据文件中，模型通过终端/SDK 按需读取和计算，不需要将整张历史行情表装入对话。可引用计算必须绑定实际输入、计算脚本、数值、单位与时间，再经 register_calculation 留存和复算。

### 联网

当前 search_web 调用方舟 Plan 的 Responses 接口与 web_search，要求实际搜索事件完成，并读取 API 返回的引用注释。模型写出的搜索总结不作为网页原文。需要核对正文时，用 fetch_webpage 独立抓取和保存。

### 短期 memory

LangGraph checkpoint 保存本次会话、计划、工具状态和历史消息。它提供状态持久化，不自动保证上下文经过最佳压缩或证据组织。

### 长期 memory

SQLite/FTS 保存来源、正文版本、文章时间和系统首次取得时间，关联事件修订与历史研究。当前候选选择使用字符 TF-IDF、相关性、MMR 或 coverage；coverage 是带依赖和长度约束的启发式集合选择，长度是 UTF-8 估计，非实际模型 token。

这是检索增强的研究流程，目前主要是词法检索和证据选择，不应笼统描述为已有完整向量 RAG 或语义知识图谱。

## 5. 下一阶段的 Jev 三个接入点

| 位置 | 判断内容 | 后续使用 |
|---|---|---|
| 入库分类 | 资产、主题、事件状态 | 辅助检索索引与事件关联，按内容/模型/判据版本缓存 |
| 检索后上下文选择 | 相关性、重复、更新、更正、潜在矛盾 | 将语义信号交给程序进行证据集合选择；保留来源和重要反证 |
| 报告后核验 | 声明相对给定原文是支持、矛盾或信息不足 | 形成修订或补查反馈，先旁路评测，未经验证不替换现有发布审核 |

冲突不直接触发删除。先对齐资产、事件、时点与统计口径，区分状态更新、范围不同和真正矛盾。重要的未解决冲突保留双方，必要时补查；较新、较多数或较高置信不自动等于真实。

Jev 给出局部语义信号；检索、时间校验、原文管理、长度约束和集合选择仍由系统执行。涉及数值和精确时间的检查继续使用代码。

## 7. 建议实施顺序与验收

### 第一阶段：统一任务定义和冻结验证材料

为三个接入点定义共享输入/输出、证据身份、时间字段、判据版本和不确定选项。优先收集原始新闻、真实更正/更新及问题，预写可回读原文的标签；按事件和时间划分开发与未查看的确认集。先建立人工可审核的标签草稿，再进行独立复核，不把模型自己的判断当真值。

### 第二阶段：建立可替换的判断组件，优先研究上下文选择

使用同一接口接 local 词法基线、豆包语义判断和 Jev 语义判断，先在冻结材料上运行。第一版保持主 harness、主生成模型和发布检查不变，不为每个内部步骤扩展新的模型可见业务工具。共享缓存和证据收据，模型或判据变更使旧判断失效。

### 第三阶段：分别评测与消融

分类比较每类 precision/recall/F1、混淆矩阵和弃权；上下文比较关键证据召回、重复、反证/更正保留、长度和后续报告质量；核验比较支持/矛盾/不足识别与漏报。冻结相同候选池、问题、上下文约束、主生成模型和实际模型版本，分别比较豆包与 Jev，再单点替换和组合。

记录完整流水线的请求次数、输入/输出 token、缓存命中、失败、重试、平均及尾部延迟。豆包 Plan 的额度消耗、Jev 的按量费用和端到端开销分别报告；不直接用官网宣传倍率或套餐标称价格代替实际测量。报告质量采用盲化、独立人工可审查标签，不用同一模型自评分。

### 第四阶段：通过后以开关接入产品

先让新判断在旁路中留下收据，验证不会遗漏来源、更正、关键反证或历史截止限制，再按单个接入点启用。补齐“错误声明—新来源—更正理由—受影响报告”的反馈链。保留现有单 agent 基线，后续再单独研究更复杂的 agent 分工。
